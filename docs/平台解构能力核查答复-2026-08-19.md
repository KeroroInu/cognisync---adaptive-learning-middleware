## 0. 先看结论：论文能用什么、不能用什么

在展开之前，先给三条对论文最重要的判断，因为它们会直接改变你怎么写「平台支撑」那一节。

**第一，「解构过程」的证据链是真实存在且质量不错的。** `stage_artifacts` / `artifact_versions` 是追加式版本表，每次修订保存产物的**完整 JSONB 快照**而不是 diff，配 `previous_version_id` 串成修订链，配 `content_hash` 保证「内容没变就不建新版本」。这意味着「学生第一版功能卡 → 最终版功能卡」的逐字段比对是可以真实还原的，而且后端已经有在线算 diff 的导出接口。这是你论证「解构确实发生了」最硬的一块。

**第二，「人机边界」比问题清单里预设的要弱一层，但不是没有。** 平台没有你设想的那种「解构画布 + 🔒/🤖 区域标注」。真实形态是：学生在**填功能卡表单时**必须二选一回答「这部分理解责任属于谁？——我必须理解 / 可以请 AI 协助」。这是学生自主声明的，会落库、会回显、还会注入 build 阶段的 AI 上下文。所以人机边界判断**有证据**，只是粒度是「每张功能卡一次选择」，不是画布上的空间标注。

**第三，也是最需要你在论文里小心措辞的：L0–L3 是提示词约束，不是技术硬限制。** 全链路唯一一次「硬」的动作是后端对整数做了一次 `min()`，把请求等级压到教师允许的上限；压完之后所有约束都是拼进系统提示词的中文句子。LLM 返回之后，平台**不数代码行、不截断、不重试、不做任何内容校验**。而且学生端界面根本不知道自己被降级了，仍然显示他请求的那个等级。如果论文里写「平台在技术上封禁了 L3 代码输出」，是与代码不符的。

## A. 教师预解构（教学设计层）

### Q1. 教师端「项目蓝图」的完整结构？能否分填目标/知识/功能/路径四维？

**① 现状：部分有。** 四维中，**功能解构和路径解构有完整独立的编辑区，知识解构只有弱形态，目标解构没有。**

**② 实现方式。** 数据结构是 `ProjectBlueprintConfig`（`backend/app/schemas/project_blueprint.py:85`），教师界面是全屏弹层 `admin-frontend/src/pages/ResearchBlueprintEditor.tsx:274`，入口在 `ResearchManagement.tsx:669`。界面固定五个 Tab（`ResearchBlueprintEditor.tsx:43`）：

| Tab | 界面上真实能填的内容 | 对应四维 |
|---|---|---|
| 顶部身份区 | 蓝图名称 / 项目标识 / 演示标识（`:352-365`） | — |
| 01 可观察现象 | 现象描述、引用标识、证据类型（四选一：runtime_event/visual_change/score_change/error_state）、教师备注、"必须观察"勾选（`:385-435`） | **≈现象解构，不是目标解构** |
| 02 功能模块与契约 | 功能职责、模块标识、同义表达、运行情境、输入/输出/前置条件/完成后应满足（`:465-474`）；前置关系勾选（`:476-491`）；知识责任（`:493-510`）；是否必需（`:512`） | **功能解构 ✅**；知识解构（弱） |
| 03 关系与实现路径 | DAG 关系图（`ResearchBlueprintRelations.tsx:113-158`）、系统推导的建构层级（`:160-175`）、前置勾选含成环拦截（`:49-63`）、结构变体 alternatives（合并/拆分/替代 + 关联模块 + 教师说明，`:198-251`） | **路径解构 ✅** |
| 04 测试与建构支架 | 学生函数入口 functionTemplate、可视化行为标识（`ResearchBlueprintTests.tsx:125-145`）、测试用例（标识/类别/JSON 输入/JSON 预期/对学生隐藏，`:183-205`） | — |
| 05 L0–L3 辅导边界 | 见 Q3 | — |

三点需要在论文里如实处理：

**「目标解构」在 schema 里根本不存在。** `ProjectBlueprintConfig`（`project_blueprint.py:85-95`）没有任何学习目标、能力目标、素养目标字段。最接近的是 `phenomena`（可观察现象），但它的语义是「学生运行成品时应该注意到什么」，属于**观察引导**而非目标分解。如果论文要论证「教师做了目标解构」，目前**没有平台证据**。

**「知识解构」只是挂在功能节点下的标签列表。** `BlueprintKnowledgeItem` 只有两个字段：`labelZh` 和 `responsibility`（`project_blueprint.py:22-24`），后者三选一：`student_core`（学生核心判断）/ `ai_supported`（AI 可提供支架）/ `generated_process`（过程自动生成）。没有知识点之间的关系、没有难度分级、没有与 Neo4j 知识图谱的关联。它是「功能解构的附属属性」，不是一个独立的知识结构。

**蓝图有完整的版本化与发布机制。** 表 `project_blueprint_versions`（`backend/app/models/sql/research.py:227-235`），草稿走 `PUT /research/tasks/{id}/blueprints/draft`（`admin/research.py:525-577`，同任务只维护一个草稿，存在则原地覆盖），发布走 `POST .../{blueprint_id}/publish`（`:580-621`），发布前跑 `validate_blueprint_for_publish`（`project_blueprint.py:109`）校验非空、悬空前置、自依赖、**成环**、变体引用。学生首次上报关键事件时冻结所用版本（`endpoints/research.py:473` → `ResearchTaskSubmission.blueprint_version_id`）。**这一点对论文有用**：意味着每条学生数据都能追溯到当时生效的教师蓝图版本，教师中途改蓝图不会污染已有数据。

**③ 能否导出/展示：可以，但要手工。** 蓝图 JSON 可通过管理端 API 读出；教师可从零创建（`lib/projectBlueprint.ts:115` 的 `createEmptyBlueprint`，调用点 `ResearchBlueprintEditor.tsx:102`），不依赖种子数据。补充一个事实：`docs/teacher-blueprints/snake-project-v2.json` 是**唯一**的示例蓝图，且**不是种子数据**——全仓库没有任何代码引用它，编辑器里也没有 JSON 导入按钮，要灌进去只能手工调 API。

### Q2. 六阶段是平台固定死的，还是教师可自定义？

**① 现状：完全硬编码，教师不能增减；而且阶段列表在仓库里有三种互不一致的版本。**

**② 实现方式。** 全仓库没有任何增删阶段的 UI 或 API。阶段列表至少在八处各自写死，其中三处内容不同：

- `backend/app/schemas/project_blueprint.py:10` —— 6 个，第六个是 **`transfer`**
- `backend/app/models/sql/research_event.py:78-90` —— `ProjectStage` 6 个，第六个是 **`reflect`**（注释 `:81-82` 自己承认是为容纳迁移反思额外加的）
- `backend/app/schemas/chat.py:76` —— `ProjectScaffoldContext.stage` 只有 **5 个**，`transfer` 和 `reflect` 都没有
- `backend/app/services/scaffold_service.py:13-19` —— `STAGE_GOALS` 只有 5 个 key
- 学生端 `frontend/data/snakeProjectBlueprint.ts:3`、`frontend/types.ts:68`、`ProjectFactory.tsx:61-74` —— 只有 **5 个阶段的界面**
- `frontend/services/stageEvents.ts:31-32` 的注释明写「后端比前端多一个 `reflect`」

**这个不一致有实际后果，必须如实报告：** 教师在「05 L0–L3 辅导边界」里为 `transfer` 阶段配置的策略**永远不会生效**。因为 `resolve_scaffold_rule` 用 `context.stage` 去查 `policy.stageLevels`（`scaffold_service.py:53`），而 `context.stage` 的类型根本不接受 `transfer`；同时数据库事件枚举里的 `reflect` 在蓝图 `stageLevels` 里没有对应的键。学生端也没有第六阶段的界面。

**③ 论文影响。** 「六阶段」这个说法目前只在**教师蓝图的数据结构层面**成立六个；**学生实际走完的是五个阶段**（observe → decompose → model → plan → build）。如果论文要写六阶段，需要说明第六阶段（迁移/反思）当前是设计而非实现，或者把它描述成课堂线下环节。

**实现代价（若要真正打通六阶段）：** 小。需要改 `ProjectScaffoldContext.stage` 的 Literal、给 `STAGE_GOALS` 加一项、统一 `transfer` 与 `reflect` 的命名（建议二选一并写迁移脚本）、学生端加一个阶段视图。估计半天到一天。**若要做成「教师可自定义阶段」，代价则很大**——阶段名散落在两个前端和数据库枚举里，需要改成配置驱动，估计一周以上，且会破坏现有数据的枚举约束。不建议为论文而做。

### Q3. 教师能否为每个阶段分设「支架层级上限」和「该阶段的解构任务」？

**① 现状：分阶段的 L0–L3 内容有；分阶段的「上限」没有（上限是全局单值）；「该阶段的解构任务」没有。**

**② 实现方式。**

*分阶段 L0–L3 定义 —— 有。* `scaffoldPolicy.stageLevels` 是 `dict[stage, list[BlueprintScaffoldLevel]]`（`project_blueprint.py:74`），每一级可编辑三个字段：本级目标 `goalZh`、AI 允许怎么帮 `allowedHelpZh`、最多补全代码行数 `maxCodeLines`。界面在 `ResearchBlueprintScaffolds.tsx:130-160`，有一键恢复默认（`:60-65`），平台默认值在 `lib/projectBlueprint.ts:23-80`。

*分阶段上限 —— 没有。* `coreImplementationMaxLevel` 是**整份蓝图一个值**（`project_blueprint.py:73`），界面上是一个下拉（`ResearchBlueprintScaffolds.tsx:101-112`）。而且后端**只在 `stage == "build"` 时用它做 clamp**（`scaffold_service.py:45-49`），其余四个阶段这个值完全不起作用——observe/decompose/model/plan 阶段学生请求 L3 就会拿到 L3。

所以问题清单里「build 阶段核心实现封顶 L2 是怎么设置的」的准确答案是：**教师在 05 页选一个全局下拉值 `coreImplementationMaxLevel=2`，这个值只在 build 阶段生效，机制是 `applied_level = min(requested_level, 2)`。**

*该阶段的解构任务 —— 没有。* `BlueprintNode`（`:44-54`）和 `BlueprintPhenomenon`（`:14-19`）都**没有 stage 字段**，蓝图内容无法按阶段分派。教师不能说「这三个功能模块在 decompose 阶段处理，那两个放到 plan」。

**③ 论文影响与实现代价。** 若论文需要「教师可为每阶段设不同支架上限」，改动很小：把 `coreImplementationMaxLevel: int` 改成 `dict[stage, int]`（保留旧字段做兼容默认值），改 `scaffold_service.py:45-49` 的取值逻辑，加一个 UI 下拉。约半天。

## B. 学生主动解构（学习过程层）

### Q4. 学生在 decompose 阶段具体做什么？

**① 现状：decompose 阶段没有任何画布或拖拽，是「选一张观察卡 + 填一张结构化表单」。画布出现在 model 和 plan 两个阶段。**

**② 实现方式（四个阶段的真实交互形态）。**

**decompose（`frontend/components/ProjectFunctionStage.tsx`）** —— 纯表单。左栏点选自己写的观察卡（`:343-360`），右栏依次填六项：程序职责单行输入（`:377-385`）、"为什么它应该成为一个独立功能"四选一 + 自由输入（`:387-411`）、输入/输出两个框（`:438-457`）、知识点多选最多 4 项（`:459-474`）、验证方式单选（`:476-491`）、责任归属二选一（`:413-436`，详见 Q5）。**六项全填齐才能保存**（`:125-134`）。保存后自动调 `suggestResearchFunctionMapping` 拉取教师蓝图的契约候选，学生可以勾选、可以全部拒绝、也可以暂不映射（`:156-207, 286-307, 560-580`）。需要 ≥2 张功能卡才能进入下一阶段（`:596`）。全文件无 canvas、无 drag。

**model（`ProjectMechanismStage.tsx`）** —— 真画布，**每张功能卡各画一张内部流程图**。5 种图形调色板（`:79-85`）、可点击也可拖入（`:480-496`）、指针拖动节点（`:227-266`）、四向连接点拖线并自动吸附（`:348-422`）、70%–140% 缩放（`:73-74`）。确认门槛：≥3 节点 + ≥2 连线（`:498-499`）。

**plan（`ProjectPathStage.tsx` 中的 `ProjectSystemPathStage`，`:202` 起）** —— 第二块画布，节点就是功能卡本身。从右侧素材区拖入（`:404-427, 950-972`），连线即前置依赖，`derivePrerequisites` 反推关系（`:123-149`），有环检测（`:151-164, 441-443`），实现顺序由连线拓扑生成（`:245`）。存在环或有未连线卡片时禁止进入 build（`:1013`）。

**build（`ProjectBuildStage.tsx`）** —— 左侧可运行的贪吃蛇预览，右侧逐模块代码编辑 + `runPythonModuleTest` 真实执行（`:563`）。

**一个对论文实验设计非常关键的事实：只有 `experimentGroup === 'pdt'` 的学生才看到真画布。** 其他实验组的 model / plan 阶段是静态占位卡片 `ProjectStagePreview`（`ProjectFactory.tsx:422-457`，路由判断在 `views/Research.tsx:1062, 1080`）。这既是好消息（对照组设计已在代码里落实）也是必须写清楚的边界（非 pdt 组不产生画布类产物数据）。

**③ 能否导出：能，见 Q6。**

### Q5. 有没有「解构画布」让学生标记哪些自己懂、哪些交给 AI？

**① 现状：没有画布形态的人机边界标注；但学生端确实有一个自主声明责任归属的必填入口，在功能卡表单里。**

**② 实现方式。** 需要把两个东西严格分开，它们经常被混淆：

*教师侧的 `responsibility`（三值，学生看不到）。* `student_core | ai_supported | generated_process`，定义在 `project_blueprint.py:11, 24`，编辑入口 `ResearchBlueprintEditor.tsx:52-54, 496`。**这三个字面量在学生端整个前端不存在**（已全仓 grep）。下发给学生的映射建议只包含 `node_id / title_zh / match_reasons / score`（`frontend/types.ts:286-291`；后端 `endpoints/research.py:405-409`），教师的责任归属**不在其中**。所以它是教师的教学设计标注，不是学生的边界判断。

*学生侧的 `responsibilityOwner`（二值，学生自己选）—— 这才是你要的证据。* `ProjectFunctionStage.tsx:413-436` 有一个 fieldset，标题「这部分理解责任属于谁？」，两个按钮：**「我必须理解」/「可以请 AI 协助」**，写入 `responsibilityOwner: 'student-core' | 'ai-supported'`（`:42, 111, 223`）。它是**保存功能卡的必填项**（`:133`），卡片上会回显（`:531-533`），会作为产物内容上报到版本链（`frontend/services/stageEvents.ts:225`），还会注入 build 阶段的 AI 上下文（`ProjectBuildStage.tsx:458`，拼成"理解责任：AI 可协助、学生验证 / 学生核心责任"）。

**③ 论文可以怎么用（这是本次核查最有价值的一条）。** 你可以合法地论证：平台要求学生在解构阶段**对每一个自己划出的功能模块，显式声明人机责任归属**，并且这个声明会真实影响后续 AI 的上下文。数据上你能算出：每个学生的 `ai-supported` 比例、这个比例随阶段/时间的变化、以及它与实际求助等级分布是否一致（后者是很好的「元认知准确度」代理指标——声称"我必须理解"却在该模块反复请求 L3，就是边界判断与实际行为的背离）。

**但不能写的三件事：**（1）不能写「解构画布上可标注人机边界」——`StudentFlowNode` / `StudentDiagramEdge`（`frontend/data/projectPath.ts`）没有任何责任归属字段，两块画布上没有这个交互；（2）不能写学生看得到教师的责任预设；（3）不能把 L0–L3 说成「学生声明边界」——`ProjectScaffoldAssistant.tsx:94` 各阶段等级从 0 起，只能靠"再具体一级"按钮逐级递增（`:195-199, 279-281`），学生不能预先声明"这块交给 AI"。

**文档核对：** `docs/STUDENT_FRONTEND_DESIGN.md:225` 提到的"学生项目解构画布"位于第 12 节「**准实验实施前的功能完善清单**」，文档自身就标注为待完善；同节 230 行的"功能卡增加边界理由和责任标签"则已实现。**不要把该文档当成已实现功能引用。**

### Q7. L0–L3 是 prompt 约束还是技术硬限制？

**② 实现方式（完整调用链）。**

1. **等级由前端 state 决定并上送。** `ProjectScaffoldAssistant.tsx:94` 初始化各阶段 level 为 0，`:196` 的"再具体一级"按钮做 `Math.min(3, level + 1)`，`:166` 把 level 塞进 `scaffoldContext`。

4. **进提示词。** `chat.py:848-854` 追加 `build_scaffold_prompt(...)`，生成 `COGNISYNC_SCAFFOLD_MODE` 段（`scaffold_service.py:235-250`），其中 `:242` 写着「本轮最多允许补全代码 {code_limit} 行；0 表示不允许生成代码」。

**③ 论文措辞建议。** 准确的表述是：「平台通过教师蓝图策略对支架等级做**输入侧钳制**，并将等级边界、允许的帮助方式与代码行数上限以结构化系统提示词的形式约束 LLM 输出；输出侧的合规性依赖模型遵循，平台记录了请求等级与实际生效等级的差异以供事后审计。」这样写既真实又不弱。**不要写「技术上封禁」「强制拦截」。**

**实现代价（若要加输出侧校验）：** 小。在 `chat.py:935` 之后加一个函数，正则提取回复中的代码块、数非空行、超过 `policy_max_code_lines` 则或截断或触发一次带更严格指令的重试，并把 `violated` 记进 `scaffold_events`。约半天。**如果论文答辩时老师会追问这一点，这半天很值得投入**，因为它能把「prompt 约束」升级成「可验证的硬约束 + 违规率统计指标」。

### Q8. coreImplementationMaxLevel=2 的具体机制？学生反复索要会怎样？

**① 现状：会被降级，但只在 build 阶段；学生对降级完全无感知；平台不会拒绝、不会告警、不会限流，学生可以无限次索要。**

**② 实现方式，分三点。**

**(a) clamp 只在 build 阶段，且必须有有效蓝图。** `scaffold_service.py:48` 是 `if context.stage == "build":`。observe / decompose / model / plan 四个阶段请求 L3 就直接给 L3。更进一步，`:45` 是 `if policy:`——若学生绑定的蓝图为空或校验失败（`chat.py:186-194` 会把 policy 置 None），则 `:44` 的默认值 `max_implementation_level = 3` 生效，**build 阶段也不做任何 clamp**。默认 `coreImplementationMaxLevel=2` 定义在 `project_blueprint.py:73`。

**(b) 学生端不知道被限制了，而且显示的是错的等级。** `ChatResponse`（`schemas/chat.py:134-142`）只有 `message / analysis / updatedProfile / updatedGraph`，**不含任何 scaffold 元数据**。两个前端 grep `wasClamped` / `policyWasClamped`：**零命中**（已复核）。`ProjectScaffoldAssistant.tsx:173-179` 用学生**请求**的等级打气泡标签，`:262` 渲染 `L{message.level}`。所以：**学生请求 L3、实际被降到 L2 时，界面依然显示「L3 · 最小补全」。** 唯一提到降级的是提示词里对模型说的一句「如请求被限制，不得隐瞒这一差异」（`scaffold_service.py:238`）——是否告知学生取决于模型是否照做。

**(c) 没有任何风险信号机制。** `was_clamped` 的全部去向只有两处：写入 `scaffold_events` 表（`research_event_service.py:603`）、导出 CSV（`export.py:741` 及 `:217, 328`）。**没有连续 clamp 计数、没有阈值、没有教师端告警、没有限流、没有冷却。** admin 端唯一涉及 `scaffold_events` 的是 `admin/users.py:251` 的行数计数，用途是删除用户前的证据保护，不是分析。

**③ 论文可用性。** 「学生反复索要核心代码」这个行为**有原始数据可复现**（同一 `current_module` 上连续多条 `requested_level=3 & was_clamped=true` 的 `scaffold_events`），但**平台当下不做任何判定或干预**。论文里可以写成「平台完整记录了支架请求与钳制轨迹，为事后识别过度依赖提供了数据基础」，不能写成「平台会识别并阻断风险外包」。

**实现代价：** (b) 前端显示真实等级，很小——`ChatResponse` 加一个可选 `scaffold` 字段回传 `appliedLevel/wasClamped`，前端改两处渲染，约两小时，且向后兼容（旧前端忽略新字段）。**这一项建议做，因为「学生被降级却以为拿到了 L3」是一个会影响实验内部效度的问题**：学生的主观求助体验与实际收到的支架不一致，会污染你对「学生感知支架强度」的任何测量。(c) 风险信号机制约一到两天。

### Q11. 三维画像怎么从过程数据更新？能否导出？

**① 现状：能更新、能导出时间序列；但三个维度的更新机制**不同质**，behavior 维度存在一个与你研究目标相冲突的设计。**

**② 实现方式。** 线上唯一路径是 `apply_delta_with_graph_cognition`（`chat.py:804-812`）：

- **cognition —— 不用 LLM delta。** 由 Neo4j 的 `calculate_cognition_from_graph` 直接算出并**覆盖**；图谱不可用时保留旧值（`profile_service.py:158-170`）。
- **affect / behavior —— 旧值 + LLM delta，clamp 到 [0,100]**（`profile_service.py:150-156`）。delta 来自 LLM 结构化输出，先 clamp 到 [-10,10]（`text_analyzer.py:245-252`），再按 intent 二次收窄（如 help-seeking 的 behavior 只准 -1~+1，goal-setting 是 1~4，`:307-318`），再按画像上下文规则改写（`:342-432`）。LLM 失败时走关键词兜底（`:453-549`）。
- **量表不进画像。** `scale_responses` 与 profile 之间没有写入链路。
- **`behavior_logs` 是死表。** `record_session_behavior` 全仓库无调用点（仅 `behavior_service.py:25` 有定义），`calculate_behavior_from_logs` 只被同样未被调用的 `apply_affect_with_graph_cognition_and_log_behavior` 使用（`profile_service.py:195-260`）。**该表为空，不要在论文里引用。**

**更新频率：每条学生亲自输入的消息一次。** 按钮触发的支架请求**不参与分析、不更新画像**（`chat.py:742-756, 810-811`），此时 intent 被置为 `scaffold-request`、delta 全 0。这是一个**正确且值得在论文方法部分点名的设计**：按钮生成的固定句子只表示求助行为，不会被误当成学生情绪或认知证据污染画像。

**③ 能否导出：能，且已有接口。** `profile_snapshots` 是追加表，每次更新写一行，带 `source = system | user`（`models/sql/profile.py:21-67`）。可直接导出「学生 × 时间点 × 三维」长表：`/admin/export/csv/knowledge-graph`（名不副实，实为画像时间序列，`admin/export.py:249-287`）与 `/export/csv/user/{id}/trajectory`（`:412-496`）。

**一个必须警惕的效度问题。** `behavior_service.py:218-298` 的五项权重是：会话时长 30% / 频率 25% / 消息数 20% / 连续天数 15% / 概念数 10%。**消息数越多分越高——也就是说，反复向 AI 索要答案反而会推高 behavior 分。** 虽然该服务当前未被调用（死代码），但如果你在论文里把 behavior 维度解释为「自主学习行为」，这个定义与「AI 依赖」是正相关而非负相关的。建议在论文里把 behavior 明确定义为「学习活跃度」而非「自主性」。

### Q12. 校准日志（CalibrationLog）的作用？能否作为元认知能力证据？

**① 现状：表、接口、冲突判定逻辑全都实现了，但学生端从不上报，所以在真实运行中它是一张空表。**

**② 实现方式。** 字段：user_id / timestamp / dimension / system_value / user_value / conflict_level / user_comment / likert_trust（`models/sql/calibration_log.py:38-88`）。冲突判定：|差值| < 15 记 low、≤ 30 记 medium、> 30 记 high（`profile_service.py:674-690`）。系统评估值取当前最新的 `source=system` 快照（`:291`）。写入路径有两条：`PUT /profile/{id}`（`endpoints/profile.py:49-83` → `apply_user_override`，一次写 3 条日志 + 一条 `source=user` 快照）和 `POST /calibration`（`endpoints/calibration.py:23-71`）。

**关键缺陷（已复核确认）：学生端两条接口都不调。** `views/Calibration.tsx:27-39` 的 `handleSubmit` 只调 `onLogCalibration` → `services/store.ts:144-155` 写 React 内存 state，**不落库**；`frontend/services/api.ts` 全文没有 calibration 相关的 fetch，也没有任何 `PUT /profile` 调用（已 grep 确认）。`KnowledgeGraph.tsx:387-389` 同理。**结论：`calibration_logs` 现在是空表，页面上学生填的自评一刷新就没了。**

**是否反向影响画像或支架：不影响。** `apply_user_override` 只写 `source=user` 快照，而 `get_profile` 只读 SYSTEM（`profile_service.py:47, 578-592`），`get_recent_changes` 显式排除 user 快照（`:336-361`），`scaffold_service` 完全不读 CalibrationLog。**这是设计意图（学生自评不污染系统评估），不是 bug。**

**③ 能否作元认知准确度证据：模型上完全可以，但必须先补上报。** `(user_value - system_value)` 已经在导出里算好了（`admin/export.py:440`），配合 `likert_trust` 可以做偏差序列、可以做「自评偏高 / 偏低」的稳定倾向分析，也可以与 `responsibilityOwner` 的声明做交叉验证。

**实现代价：极小，且优先级最高。** 只需在 `frontend/services/api.ts` 加一个 `postCalibration` 函数，在 `Calibration.tsx:27` 的 handleSubmit 里调用它（后端接口、schema、冲突判定全都现成）。**约一到两小时。** 如果你的论文有「元认知」这一章，**这是本次核查里投入产出比最高的一处修补**——不补就等于这一章完全没有数据。

## E. 论文论证的关键证据

### Q13. 平台能否证明「解构」真的发生了？有没有前后对比数据？

**① 现状：能。这是平台数据质量最好的一块。**

**② 能证明什么。** 版本链结构是完整的：`artifact_versions` 追加式、content 保存**全量 JSONB**（不是 diff）、`previous_version_id` 串链、`uq_artifact_version_seq` 保证序号连续（`research_event.py:254-316`）。因此「第一版功能卡 vs 最终版功能卡」的**逐字段对比、修订次数、修订时点**都能真实还原，而且导出接口会在线计算相邻版本的字段级 diff（`admin/export.py:549-572, 575-631`），不需要你自己写比对脚本。

跨阶段回改也有支撑：`research_event_service.py:149-163` 有白名单，BUILD / REFLECT 阶段修订早期阶段的产物是合法且可识别的。这意味着「学生在写代码时发现自己的解构错了，回头改功能卡」这条**最有说服力的解构证据**是可追踪的。

**③ `change_source` 的判别力：部分可信，有一处已知污染。**

- 「测试失败后修改」**可区分且可靠**：`test_revision` 只在 `reviseEarlierStage` 使用（`ProjectBuildStage.tsx:522-543`），事件 detail 带 `trigger:'test_failure'`、`failedUnitId`、`lastResultCode`。
- 「自主修改」**只在 build 阶段可靠**：`structure_edit` 只用于 module_code（`ProjectBuildStage.tsx:621`）。
- 「求助后修改」**不可区分**：`scaffold_followup` 枚举定义了（`research_event.py:114`）但**前端零调用**（已 grep 全部 tsx）。
- **一处污染：** model 阶段的 `structure_change` 事件里，mechanism 产物却硬编码 `change_source='stage_confirm'`（`ProjectMechanismStage.tsx:507-516`）。所以 observation / function_card / mechanism / path 这四类**解构产物的 change_source 几乎恒为 `stage_confirm`**，该字段对解构类产物**基本没有判别力**。

**④ 现有数据能支撑的论文论证：**

- 解构产物的**修订次数与修订深度**（功能卡改了几版、每版改了哪些字段）
- **跨阶段回改率**（进入 build 后回头改 decompose / model / plan 的比例与时点）
- **测试驱动修订比例**（`test_revision` 占全部修订的比例）
- 「测试失败 → 回改哪个阶段」的**因果链**（detail 里有 failedUnitId 和 lastResultCode）
- 解构产物**质量的前后变化**（字段级 diff，比如输入输出从"未填"到填写完整、验证方式从模糊到可执行）
- 学生**契约映射的接受/拒绝行为**（function_mapping 产物记录了学生是否接受教师的契约候选，这是「学生自己的解构 vs 教师标准解构」的直接对照数据）

**⑤ 缺什么（论文局限部分需要写）：**

- **求助与修改之间的因果关联断裂**：`scaffold_followup` 未使用 + `adopted` 恒 NULL，所以无法回答「AI 的建议被采纳了吗、采纳后产物怎么变了」。
- **阶段停留时长不可靠**（见 Q10-4）。
- **错误消息原文丢失**（见 Q10-6）。
- **解构类产物的「自主修改 vs 触发修改」无法区分**（change_source 污染）。

*实现代价：* 打通「求助 → 修改」链路（在支架回复后的下一次产物修订上标 `scaffold_followup` 并回填 `adopted`），约一到两天，这是仓库注释里说的「任务 5」。修掉 mechanism 的 change_source 硬编码，十分钟。

### Q14. 平台能否区分「学生主动解构」和「AI 代劳」？

**① 现状：有可供事后推断的原始数据；已实现的判定逻辑为零。这两件事必须在论文里分开写。**

全仓库 grep `over-reliance` / `overreliance` / `plagiar` / `抄袭` / `依赖度` / `代劳` / `风险外包` / `risk_signal` / `alert` —— **无任何命中**。

**② 已落库、可供离线统计的原始数据：**

- `ScaffoldEvent`（`research_event.py:477-641`）：requested_level / applied_level / was_clamped / policy_source / policy_max_code_lines / code_length / code_fingerprint，带 `(user_id, task_id, created_at)` 与 `(stage, applied_level)` 索引。CSV 导出（`export.py:698-772`）还会关联出学生提问与 AI 回复的**原文**。→ 可离线算「L3 请求占比」「clamp 频次」「等级升级速度」「同一模块的重复求助次数」。

- **`requested_level` 分布没有聚合接口。** admin 侧没有任何按 requested_level 或 was_clamped 分组的查询。

**④ 论文措辞建议。** 可以写：「平台完整留存了支架请求等级、教师策略钳制结果、学生自主声明的人机责任归属与代码修订全量版本，为事后识别过度依赖提供了数据基础；本研究据此构建了 X 指标（由研究者离线计算）」。**不能写平台会自动识别或干预。**

**实现代价（若要做最小可用的风险外包识别）：** 三件事——(1) 给 AI 回复里的代码块也算指纹并入库；(2) 在 module_code 产物入库时与最近若干条 AI 回复代码做相似度比对，超阈值打标；(3) 把「声明 student-core 却在该模块反复请求 L3」做成一个规则。约二到三天。**对论文而言，这三件事完全可以在离线分析脚本里做，不必进平台**，除非你要论证「中间件具备实时干预能力」。
