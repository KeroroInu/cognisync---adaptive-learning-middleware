## 1. 本轮要解决的问题

当前受控创意函数已经能修改蛇、食物、得分、速度和少量对象，但学生提出新想法时仍容易遇到三类问题：

- 运行器只认识有限对象类型，增加障碍、炸弹、传送门之外的新视觉往往需要继续改 React/CSS；
- Agent 可能建议沙箱中不存在的名称、导入或状态字段，形成“能讨论、不能运行”的代码；
- 40—50 名学生同时请求 DeepSeek 时，虽已有并发限制和重试，仍缺少全局公平排队、完整幂等、排队可见性和可分析的性能指标。

本轮目标不是让学生在服务器上运行任意 Python，也不是让 Agent 动态生成前端源码，而是建立下面的稳定闭环：

```text
学生提出创意并编写 Python 逻辑
        ↓
教学智能体读取当前卡片、能力画像、教师批准教材与运行器能力
        ↓
按 L0—L3 提供可在当前沙箱运行的函数模板或代码讨论
        ↓
确定性装配器校验并组合已启用的函数
        ↓
浏览器 Worker 执行 Python，输出受控游戏状态/场景协议
        ↓
统一渲染器绘制，基础游戏在单卡失败时继续运行
```

这里的“自由度最大化”是：在统一能力协议内支持大多数二维网格游戏机制，而不是承诺任意 Python、任意第三方库、任意网络资源或任意 3D/多人游戏都能直接实现。

## 2. 不可改变的产品边界

1. 学生主流程继续是：完整项目运行与观察 → 功能卡 → 单功能流程图 → 七函数建构 → 创意扩展 → 迷宫寻宝。
2. 创意卡默认仍只要求命名并显示空白 `creative_feature(event, state)` 模板。只有学生主动求助时，Agent 才按支架等级提供填空模板或完整当前函数；不增加强制表单。
3. L0—L3 含义不变：L0 测试定位，L1 少量关键代码，L2 接近完整的填空结构，L3 一次确认后直接围绕当前完整函数讨论。
4. Agent 不得静默修改编辑器、创建/删除/启用卡片、运行代码或推进阶段。学生保留确认、编辑、测试和启用权。
5. 按键、每帧、碰撞和绘制全部在浏览器本地完成，不请求 DeepSeek 或后端。
6. 教师隐藏测试、蓝图同义词和标准答案不得进入学生 API。创意运行器能力协议可以公开，因为学生必须据此编程。
7. 三组实验条件继续由后端强制隔离。讲授组和 AI-PBL 组不能因本轮改动意外获得 PDT Agent、画像适配或分级支架。
8. 保持当前暗色网格、荧光绿色蛇、食物、计分、方向、编辑器、终端和侧栏的整体视觉。通用渲染器只替换或扩展棋盘内部绘制，不重做整个学生界面。
9. 不在首轮使用服务端为每个学生启动 pygame、Tkinter、容器桌面或视频流。这样会显著增加服务器压力，也不适合学校机房浏览器访问。

## 3. 当前已经实现的基础，不要重复开发

以下内容在基线提交中已经存在，Claude 应在其上增量扩展：

- 每位学生的工作区按认证用户和任务保存，创意卡有稳定 UUID；研究产物使用 `creative::<UUID>` 作为稳定键，并进入 `StageArtifact` / `ArtifactVersion` / `StageEvent` 证据链。
- 浏览器 Pyodide Worker 串行执行基础函数和创意函数；单次执行 5 秒超时，超时后重建 Worker。
- 创意卡相互隔离；一张卡异常不会让基础游戏或后续卡永久崩溃。
- 禁止 import、文件访问、动态执行、反射和双下划线属性；Worker 加载后关闭网络能力。
- 已公开七种创意事件：`start`、`key`、`before_move`、`move`、`eat`、`loop`、`end`。
- 可修改的顶层状态为 `snake`、`direction`、`food`、`score`、`game_over`、`interval`、`objects`。
- `objects` 当前支持 `id/type/position/label/solid/active/data`，最多 48 个；界面对 obstacle、wall、bomb、portal、bonus、shield 和 custom 有固定表现。
- `print()` 已在沙箱安全开放并进入调试终端，输出有长度和行数上限。
- Agent 已能读取当前阶段、当前基础/创意卡、当前代码与最近测试反馈；同任务、同阶段、同卡片的对话历史相互隔离。
- DeepSeek/OpenAI 兼容 Provider 已复用 HTTP 连接，当前每个 analysis/chat Provider 各自有 `LLM_MAX_CONCURRENCY` 信号量；429/5xx 重试只位于 Provider 层；分析和聊天分别有 15 秒、30 秒整轮预算；等待模型前会结束数据库只读事务。
- 前端已有 Vitest；Pyodide 已由构建脚本下载到本地静态资源。不要再把“无前端测试”或“仍依赖公共 Pyodide CDN”当成当前事实。

## 4. 目标架构：能力驱动，而不是功能类型驱动

### 4.1 Creative Capability API V2

保留现有函数签名以兼容历史卡：

```python
def creative_feature(event, state):
    return state
```

新增的不是任意系统权限，而是一组注入沙箱、无需 import 的确定性帮助函数。建议第一批能力：

```python
randint(min_value, max_value)
choice(items)
random_empty_cell(state)
add_object(state, object_spec)
remove_object(state, object_id)
move_object(state, object_id, position)
find_objects(state, object_type=None)
set_timer(state, timer_id, ticks)
timer_ready(state, timer_id)
```

要求：

- 所有帮助函数在 Python 沙箱内部实现并列入明确白名单，不能靠 `import random`、文件或网络实现；
- `random_empty_cell` 必须避开蛇身、食物、实心对象和棋盘边界；
- 随机数必须接受平台注入的种子。同一代码、初始状态、事件序列和种子应得到同一结果；
- 随机种子、能力协议版本和运行器版本要进入测试/运行证据，而不是只存在浏览器内存；
- 保留原始字典、列表和基础 Python 表达式，不能把学生限制为只调用平台函数；
- 学生可以在同一张卡中定义自己的辅助函数，但仍受同一 AST、时间、输出和状态限制。

可以在确认真实需求后增加 `object_hit`、`score_changed`、`timer`、`level_start` 等事件，但必须先定义事件负载、触发顺序、幂等语义和旧卡兼容测试，不能只在 Prompt 中写一个名称。

### 4.2 通用场景协议与统一渲染器

把当前“按 `type` 选择固定符号和 CSS”的对象渲染逐步升级为数据驱动的场景协议。建议在现有字段上兼容扩展：

```ts
interface SceneObjectV2 {
  id: string;
  type: string;
  position: [number, number];
  shape?: 'rect' | 'circle' | 'line' | 'text';
  size?: [number, number];
  color?: string;
  strokeColor?: string;
  opacity?: number;
  rotation?: number;
  label?: string;
  zIndex?: number;
  solid?: boolean;
  active?: boolean;
  animation?: 'none' | 'pulse' | 'blink' | 'spin';
  data?: Record<string, string | number | boolean>;
}
```

实现要求：

- 未提供新字段的旧对象继续按当前 type 样式绘制；
- 新对象即使 type 未知，也能依据 `shape/color/label` 绘制，不得为每个学生创意新增一个 React 组件；
- 渲染顺序至少分为背景网格、游戏实体、学生对象、效果/文字和结束遮罩；
- Python 只描述状态和行为，不能提交 HTML、CSS、JavaScript、DOM 选择器或可执行绘制代码；
- 主线程重新校验颜色、数值范围、坐标、对象数量、文字长度和 `zIndex`，不能相信 Worker 返回值；
- 限制每帧对象数、文本长度和动画类型，避免学生代码造成 DOM/Canvas 资源耗尽；
- 优先把当前棋盘内部改为一个通用渲染层，保留现有外框、得分栏、控制按钮和响应式布局。

这套协议能够表达墙、障碍、炸弹、传送门、奖励、陷阱、移动敌人、计时区域和提示文字等二维网格机制。联网、摄像头、任意图片上传、3D 和实时多人仍属于能力缺口，应由 Agent 如实说明。

### 4.3 确定性装配，不让模型直接控制运行器

Agent 可以提出“当前函数应监听哪些事件、读写哪些状态、依赖哪些能力”，但不能直接把一段未经验证的整体程序写进数据库并执行。

建议把模型建议规范为服务端可校验的结构：

```json
{
  "support": "direct | approximation | capability_gap",
  "capabilityVersion": "creative-v2",
  "eventHooks": ["eat"],
  "reads": ["food", "objects"],
  "writes": ["objects"],
  "starterCode": "def creative_feature(event, state): ...",
  "tests": ["吃到食物后新增一个对象"],
  "assumptions": []
}
```

模型输出只作为提案：后端先按 JSON Schema、能力白名单和本轮 L0—L3 边界校验，再以文本和代码块展示给学生。学生自行复制、修改和测试。运行时仍按稳定卡片顺序由确定性装配器执行已验证且启用的卡片；任何依赖循环、未声明状态、非法签名或失效卡片都应被拒绝或隔离。

## 5. Agent 如何结合学生能力与教材生成模板

### 5.1 个性化边界

学生画像只能调整：

- 一次给多少空位；
- 注释和问题的具体程度；
- 是否先给例子、变量提示或伪代码；
- 语言节奏和术语解释。

画像不能：

- 自动把学生降到更低学习目标；
- 跳过学生必须完成的阶段；
- 直接决定学生不能尝试某类创意；
- 改变三组实验条件；
- 在没有测量效度证据时把画像分数写成真实能力等级。

### 5.2 教材上下文

目前系统有教师任务提示和知识图谱摘要，但没有完成“教师批准教材的版本化检索”。因此不要把教材 RAG 写成已经实现。

目标实现应满足：

- 只有教师明确上传/选择并发布的教材片段可进入当前任务；
- 教材内容带任务 ID、版本、章节、来源和发布时间，正式实验开始后冻结；
- 每轮只检索与当前创意、当前代码和当前错误相关的少量片段；
- Prompt 中明确区分平台能力契约、教师教材、学生产物和历史对话；
- 教材只能帮助解释概念和生成模板，不得覆盖运行器真实能力；
- 保存本轮使用的教材版本和片段 ID，避免只记录最后一段自然语言答案。

如果本轮不开发教材上传/发布链路，则先把接口和版本字段留好，使用当前教师任务目标，并在 UI 和文档中明确“教材检索尚未启用”。

### 5.3 分级输出

- L0：给能直接放进当前函数、读取真实 `event/state` 的打印或断言；不能给独立测试文件或不存在的变量。
- L1：只给实现当前卡点所需的关键表达式或 1—3 行代码。
- L2：给可运行的当前函数骨架和少量 `TODO`，只使用能力注册表中真实存在的事件、状态和帮助函数。
- L3：一次确认后可给当前创意函数完整实现，并继续围绕完整代码修改和解释；不得扩展到其他卡或静默写入编辑器。

Agent 在回答前必须先判断：`直接支持`、`安全近似实现` 或 `当前能力缺口`。不能为满足学生而编造沙箱 API。

## 6. 学生独立代码与研究证据

不另建一套“Agent 创意代码数据库”。继续使用现有工作区快照与研究证据双写：

- 工作区快照：用于跨设备恢复当前状态；
- `StageArtifact`：按 `user_id + task_id + stage + artifact_type + creative::<UUID>` 定位学生当前创意卡；
- `ArtifactVersion`：保存有教学意义的代码/模板修订；
- `StageEvent`：记录创建、测试、启停、隔离、确认和删除墓碑；
- `ScaffoldEvent`：记录请求等级、生效等级、模型/Prompt/能力/教材版本和是否成功送达。

建议扩展创意产物完整快照，而不是新增孤立表：

```json
{
  "title": "障碍物",
  "studentCode": "...",
  "agentStarterCode": "...",
  "studentEdited": true,
  "capabilityVersion": "creative-v2",
  "eventHooks": ["eat"],
  "reads": ["snake", "objects"],
  "writes": ["objects"],
  "scaffoldLevel": 2,
  "modelConfigVersion": "...",
  "promptVersion": "...",
  "textbookVersion": null,
  "lastTest": {"passed": true, "seed": 12345},
  "enabled": true
}
```

只在创建、Agent 模板确认、测试、启停、显著代码修订和删除时写版本；不要记录每次按键、每帧或每个字符。访问创意产物与版本时必须同时校验当前认证用户和任务可见性，不能仅凭 artifact ID 返回。

## 7. DeepSeek API 请求优化

### 7.1 当前事实

当前实现已经具备：

- analysis/chat Provider 缓存和 HTTP 连接池复用；
- 每个 Provider 各自的 `asyncio.Semaphore(LLM_MAX_CONCURRENCY)`，默认值 12；
- Provider 层对 429/500/502/503/504 的有界重试，默认最多 2 次重试；
- `Retry-After` 的简单整数秒处理与指数退避抖动；
- analysis 15 秒、chat 30 秒的端点总预算；
- 外部模型等待前释放数据库事务连接；
- 按钮生成的固定求助不做文本画像分析；固定七函数和部分完成态直接走受控回复，不调用聊天模型。

不得在聊天端点再叠加一层重试。也不要把已经存在的信号量当作待办重复实现。

### 7.2 当前缺口

1. analysis 和 chat 各有独立 Provider/信号量，默认理论上每个后端进程可同时产生 24 个模型请求，并不是真正的全局预算。
2. 当前信号量覆盖整个重试循环，等待 `Retry-After`/退避时仍占用并发槽，供应商故障时会拖慢后续请求。
3. 没有记录排队等待、首次响应、供应商处理和重试耗时，学生只看到统一“发送中”。
4. 前端虽生成 UUID，但聊天消息、模型调用、画像分析、知识图谱和支架事件尚未形成一次请求的事务级幂等状态机。
5. 上下文当前主要按字符截断：工作区 6000 字符、代码 3000 字符、同作用域 12 条消息，不是结构化且可测量的 token 预算。
6. 没有学生级公平排队、速率限制和取消；同一学生连续点击可能占用多个槽位。
7. 当前非流式完成接口要等完整回复返回；流式输出尚未实现。

### 7.3 目标调度器

增加单进程共享的 `LLMRequestScheduler`，由 analysis/chat Provider 共用，而不是各自创建不相干的全局额度。至少提供：

- 可配置的总并发上限和 analysis/chat 子额度；
- 同一学生同时最多一个交互式 chat 请求，后续请求排队或明确拒绝；
- 按学生轮转的公平队列，避免单个学生连续请求挤占全班；
- 排队超时、生成超时和总超时分开记录；
- 请求取消：学生切换任务/卡片、关闭助手或主动取消时，尚未发给供应商的任务从队列移除；
- 只在真正发送 HTTP 请求时占用并发槽。429/5xx 退避等待应释放槽，再按重试策略重新入队；
- 正确解析整数、小数或 HTTP-date `Retry-After`，并限制最大等待时间；
- analysis 失败继续规则降级；chat 失败显示真实不可用状态，基础游戏、编辑器和本地测试继续可用。

初始并发值必须通过真实 DeepSeek 账号和目标服务器压测确定，不能仅凭本地 40 人数据库测试写死。单进程先使用内存调度器；只有部署为多进程/多副本且压测证明需要共享队列或共享限流时，再评估 PostgreSQL advisory lock、Redis 或独立队列。当前阶段不要先引入 Redis。

### 7.4 全链路幂等

以前端 `requestId` 为一次逻辑求助的稳定 ID，建议增加明确状态：

```text
received → queued → analyzing → generating → delivered
                         ↘ failed / cancelled
```

要求：

- 网络重试必须复用同一个 requestId 和相同语义指纹；
- 同一用户、同一 requestId、相同请求体返回已有状态/最终结果，不再次调用模型；
- 同键不同内容返回 409；
- 用户消息、求助事件只能创建一次；
- `ScaffoldEvent(delivered)` 只在完整回复保存并实际送达后创建一次；
- 超时或断连要留下 failed/cancelled 状态，不能伪装为 delivered；
- 不因幂等重放重复更新画像、知识图谱或代码版本。

可以使用现有消息/事件表和请求 ID 约束实现；若新增轻量请求状态表，必须提供迁移、权限、清理周期和导出说明，不能把它做成研究证据之外的数据孤岛。

### 7.5 上下文和调用次数优化

- 继续按 `task + stage + focus` 只发送当前作用域历史；不同创意卡绝不混用。
- 将工作区摘要改为结构化字段优先：当前卡、代码签名、最近测试、相关观察/流程和已启用依赖；避免每轮发送整个工作区文本。
- 为 system prompt、历史、当前代码、教材片段和输出分别设 token 预算；超预算时优先保留当前代码与最近失败证据。
- 旧消息先做确定性摘要或版本化摘要，不能每轮让模型重新总结全历史。
- 缓存能力注册表、冻结教材片段和不含个人数据的 Prompt 片段；不要缓存或跨学生复用个性化最终答案。
- 固定完成态、覆盖检查、运行器错误翻译和已知 L0 诊断继续使用本地规则，避免不必要调用。
- 一次“生成创意模板”只调用一次聊天模型：结构化提案和给学生看的说明应来自同一次有效响应，不再额外调用第二个“评价模型”。
- 学生自由输入是否参与画像分析保持现有研究规则；不能为了省 API 擅自删除实验设计需要的分析。可以在压测后将分析角色换成较轻模型或规则，但要冻结并记录实验配置。

### 7.6 流式输出和前端状态

流式输出主要改善感知延迟，不会自动减少 DeepSeek 的计算压力，放在调度、幂等和指标之后实施。

若供应商兼容流式响应，可新增 SSE：

- 前端显示“排队中 / 正在分析 / 正在生成 / 正在重试”，而不是一个无差别转圈；
- 首个 token 到达后逐段显示，但只有完整结束、消息入库成功后才记为 delivered；
- 断流时明确显示未完成，可用同 requestId 恢复状态，不能把半段答案当正式支架；
- 客户端关闭连接要向调度器传播取消信号；供应商已经开始且无法取消时，仍需正确记录成本和最终状态；
- 流式内容同样执行长度、代码边界和敏感数据检查。

### 7.7 指标与隐私

至少记录并按角色、模型、任务用途聚合：

- 请求数、供应商实际调用数、重试数、取消数、规则降级数；
- P50/P95 排队时间、首次 token 时间、供应商时间、总时间；
- 429、超时、5xx、格式校验失败和最终失败率；
- 输入/输出 token（供应商返回时）、估算成本；
- 当前队列长度和并发槽使用率。

日志不得包含 API key、完整教材、完整学生代码或全部对话正文。API key 只能保存在后端配置，不得下发浏览器。研究导出需要的是请求状态、版本与耗时，不是运维日志中的秘密内容。

## 8. 性能与服务器压力判断

目标架构将主要计算放在学生浏览器：Pyodide 执行 Python，统一渲染器绘制每帧；服务器只保存关键版本/事件并处理学生主动发起的 Agent 请求。因此它比“每位学生一个服务端 Python 游戏进程”更适合 40—50 人课堂。

主要压力来源和处理方式：

| 压力 | 处理方式 |
|---|---|
| Pyodide 首次下载 | 继续自托管、强缓存，正式机房做冷/热缓存验收 |
| DeepSeek 同时请求 | 共享公平队列、全局并发预算、退避释放槽位 |
| 大上下文 | 作用域过滤、结构化摘要、token 预算、冻结片段缓存 |
| 频繁保存 | 工作区合并保存；研究证据只记录关键时刻 |
| 复杂场景绘制 | 浏览器对象数、文字、动画和每帧时间上限 |
| 恶意/错误代码 | Worker 超时、AST 白名单、状态校验、逐卡隔离 |

DeepSeek API 仍可能因供应商限流、网络或目标服务器带宽而变慢。上述设计只能控制并发放大、排队公平和失败恢复，不能保证外部供应商永不拥堵。

## 9. 开发顺序与提交边界

不要把以下内容合并成一个大提交：

1. **能力契约与测试**：定义 V2 事件、帮助函数、场景对象 Schema 和向后兼容测试；暂不改 UI。
2. **确定性沙箱能力**：实现 seeded random、对象/计时帮助函数、主线程校验和逐卡隔离测试。
3. **通用棋盘渲染**：在保留当前皮肤和布局的前提下支持 shape/color/size/zIndex/受控动画；验证未知 type 无需新增组件。
4. **创意产物版本字段**：在现有证据链中补 capability/prompt/model/textbook/seed/test 元数据和访问控制测试。
5. **Agent 结构化创意提案**：复用现有 Harness 和 L0—L3；服务端校验结构化响应，学生确认后自行编辑，不增加 Agent 执行权限。
6. **DeepSeek 调度与幂等**：共享队列、公平性、退避释放、取消、请求状态和指标；不要同时改创意渲染代码。
7. **上下文预算与可选流式输出**：结构化摘要、教材版本接口、SSE 和前端状态；流式可作为独立提交。
8. **完整验收**：浏览器、三组实验条件、并发、断网、刷新和证据导出。

每项提交前：

- 检查完整 diff 和 `git diff --check`；
- 后端执行改动文件 Ruff、针对性 pytest 和全量 pytest；
- 学生端执行 `npm run type-check`、`npm test -- --run`、`npm run build`；
- 涉及教师端时执行 lint、测试和 build；
- 重建本地服务并做真实浏览器验收后再提交；
- 显式暂存文件，不使用 `git add .`；
- 不推送远端。

## 10. 必须通过的验收矩阵

### 10.1 功能与兼容

- 空白新学生可以创建创意卡，默认只有名称和空白函数，不被强制填写额外表单。
- `kero` 历史创意卡、原七事件和旧 objects 字段继续可运行，不被迁移覆盖。
- 障碍、炸弹、传送门、奖励和一种未知自定义对象使用同一通用协议绘制，未知对象不新增专用 React 组件。
- 学生创建两个相互独立的创意卡，一张异常/死循环时另一张和基础游戏继续运行。
- 同一 seed、代码、状态和事件序列输出完全一致；不同 seed 可产生受控差异。
- import、文件、网络、eval/exec、DOM/JS 注入、非法颜色/超长文本/超量对象均被拒绝或截断。
- Agent 只使用真实能力 API、`event.get(...)`、`state.get(...)` 和 `[x, y]` 坐标；不再生成当前沙箱不能执行的测试。
- Agent 能如实区分直接支持、近似支持和能力缺口。
- 刷新后恢复当前卡、学生代码、Agent 模板来源、测试、seed、启用状态和 L3确认。

### 10.2 API 与降级

- 40—50 名独立学生同时求助时，数据库连接不被模型等待占用；共享并发不超过配置值。
- 公平队列下，一个学生连续请求不能让其他学生永久饥饿。
- 429/5xx 退避期间不占用 HTTP 并发槽；仅 Provider/调度层重试一次策略，不出现端点叠加放大。
- 同 requestId 重放不会重复模型调用、用户消息、画像更新、知识图谱更新或支架事件；同键不同内容返回 409。
- DeepSeek 超时或断网时，学生仍能编辑、运行基础游戏、测试创意和查看终端；界面明确说明 AI 暂不可用。
- 学生切换卡片或取消排队后，旧回复不会错误写入新卡片会话。
- 指标能够区分排队、供应商、首次 token 和总耗时；日志不泄露密钥、完整代码和隐藏测试。

### 10.3 实验与界面

- PDT、AI-PBL、Lecture 三组权限和 Agent 可见性保持原设计；迁移测试的教师 AI 开关仍由后端强制。
- `1280×720` 与 `1366×768` 下游戏、代码、终端、创意侧栏和可缩放助手都可达，无横向挤压。
- 每帧、按键和对象动画在网络面板中不产生 API 请求。
- 教师单生详情能按学生查看创意版本、支架等级、测试与隔离事件，但不把画像解释为客观能力排名。

## 11. 明确不做

- 不让 Agent 自主改写或运行学生代码；
- 不引入多智能体协商作为本轮前置条件；
- 不在服务器运行任意 Python、pygame 或每生容器；
- 不允许任意 pip、文件、网络、DOM、JavaScript 或系统命令；
- 不为每个新创意手写前端组件；
- 不默认引入 Redis；
- 不把“设计目标”写成“已经实现”，不把浏览器验收写成学习效果证据；
- 不承诺所有可能想法都可实现。首版目标是无需修改平台源码即可完成大多数二维网格游戏机制。
